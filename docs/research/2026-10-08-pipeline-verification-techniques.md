# Pipeline verification techniques: identity, experience, freshness, geo, challenges, reliability

Date: 8 October 2026. Scope: verification, extraction, and pipeline reliability for Launchpad. Read-only research. No crawler, job-pull, test, or network run against job sites was done. No repo file was changed except this one.

## Summary

1. The worst live bug is identity collapse. Two different employer requisitions on `careers.acme-corp.com/jobdetails?jobId=R-1001` and `...jobId=R-1002` both become `jobId = "jobdetails"` and dedup key `naukri|jobdetails`. A real run would drop one role as a duplicate. [L]
2. Workday and Lever ID extraction are wrong for common URL shapes. Workday returns the whole title slug. Lever returns null when the URL ends in `/apply`. [L]
3. The bot-block check never reads the Cloudflare `cf-mitigated` header. [L by reading, V for the header spec]
4. The experience parser handles the five Accenture fixtures correctly, but the fixtures cannot catch its misses. Word numbers with a digit in brackets fail. Alternatives ("a degree or 4 years") count as hard requirements. [L]
5. Use regex as the primary experience extractor. Add a small LLM pass only for rows the regex leaves null or ambiguous, and require a verbatim quote from the JD. Do not switch to an LLM-only extractor without a labeled set.

### Best practice for canonical URLs and dedup keys

Keep the identity-bearing part of the URL and drop the rest. Use an allowlist of query keys per host, not a blocklist of tracking keys. A blocklist misses new trackers, and an allowlist makes an unknown key harmless. The existing `canonicalizeUrl` in `job-pull/candidate.mjs` uses a blocklist (`utm_`, `fbclid`, `gclid`, `source`, `ref`). It keeps every other key, including the ones that matter (`jobId`), and that is correct. The problem is in the extraction step, not the canonicalizer. [L by reading]

Use the provider's own ID before the URL. Use the canonical URL only when no ID exists. Use company|title|location only as a last resort, and flag it weak. This matches `candidateDedupKey` in `job-pull/candidate.mjs`. [L by reading]

Keep the ID only if it contains a digit and is not a generic word. Generic words seen in the wild include `jobdetails`, `job`, `jobs`, `details`, `apply`, `careers`, `view`, and locale tags like `en-us`. [U synthesis, based on the probe below]

### Proposed identity algorithm for this repo

```
identity(url, provider, tenant):
  u = canonicalize(url)                    # lowercase host, drop fragment, drop tracking keys
  id = null
  if provider has a path rule:             # ats-specific, see table in G
      id = pathRule[provider](u.path)
  if id is null:
      for key in IDENTITY_QUERY_KEYS:      # jobId, gh_jid, req, jobReqId, job, career_job_req_id, currentJobId, jk, id
          if u.query has key: id = value
  id = trim(id)
  if id is null or no digit in id or id in GENERIC_WORDS: id = null
  if id:  return "{provider}|{tenant}|{id}"  # tenant = ATS board slug, not display company name
  return "url|" + u                          # weak key, flagged
```

After original-employer resolution, keep both keys. The lead's portal key (for example `naukri|nk-061026910126`) and the ATS key (`greenhouse|acme|4012345`) must both match the same record. Right now `mergePatch` overwrites `provider` and `jobId`, so the portal key disappears. The same role then looks new on the next run. [U by reading `crawler/original-listing-resolver.mjs` `mergePatch`; not run end to end]

## B. Experience extraction

### What the repo does now

`extractExperienceYears` in `job-pull/candidate.mjs` uses three regex passes: forward ("minimum", "at least", "must have", "requires"), reverse ("3 years of experience"), and activity ("3 years development"). It removes education, company tenure, and preference clauses, and it keeps the largest lower bound. This is a deterministic, auditable approach, and it is the right base.

### Results on the fixture [L]

I ran `extractExperienceYears` on the five rows in `tests/fixtures/experience/accenture-captured-2026-10-06.json`. Parsed minimums were 2, 3, 2, 2, 5. These match `expectedMinimumYears` for every row. The handoff's claim matches this. [L]

The fixture has a limit. Every row says "Minimum N year(s) of experience is required". The max-reducer also hides misses: row 2 contains "Minimum two (2) years" and "Minimum One (1) year", but the explicit "Minimum 3 year(s)" wins. The fixture cannot catch a missed word-number. [L by reading row text]

### Probes that expose misses [L]

| Input | Output | Expected | Problem |
|---|---|---|---|
| `Minimum two (2) years of experience in Java.` | `null` | 2 | Word number followed by a digit in brackets is not matched. |
| `Requires 5+yrs experience in backend.` | 5 | 5 | Correct |
| `Experience of 1 to 3 yrs preferred.` | `null` | none, preferred | Correct |
| `A degree or 4 years of experience in software.` | 4 | ambiguous | "or" alternative is treated as a hard requirement. |
| `Requires 3 years of relevant experience, or 2 years of experience with a Masters degree.` | 3 | ambiguous | Takes the stricter branch. Probably right for the fail-closed rule, but still a choice to document. |
| `Must have a Bachelor degree with 4 years of full time education. Minimum 1 year of relevant work experience.` | 1 | 1 | Education years excluded. Correct. |
| `We have 3 years of experience hiring engineers. Open to freshers with 0-1 years of experience.` | 0-1 | 0-1 | Company tenure excluded. Correct. |
| `We are a 10 year old company. Entry-level role, 1+ years experience.` | 1 | 1 | Correct |

Other known pitfalls, from search results [S]:
- Application-form screening questions read as requirements. One GitHub issue reports "Do you have at least 3 years of experience?" being read as a hard requirement. https://github.com/ritsth/job-autofill-extension/issues/366
- Required versus preferred is the hardest split. A paper on job-posting feature extraction reports experience as one of the weaker features to label: a DistilBERT classifier scored F1 0.59 on experience, against 0.78 for remote type. The labels came from a larger LLM, not from experts. https://pith.science/paper/2501.07663 ; https://arxiv.org/html/2602.18550v1 for the required and preferred split in a resume-screening system. [S] Neither figure was opened or checked against the paper body.

### Regex or LLM

Recommendation: keep regex as the primary extractor. Add an LLM only as a second pass, and only where the regex returns null or a range with an alternative clause.

Reasons:
- The regex is deterministic. Every decision has a visible evidence string, and it runs in the daily pipeline with no network or cost.
- Reviewing a wrong LLM answer is harder than reviewing a wrong regex answer, unless the LLM is forced to quote its evidence.
- No public source I found benchmarks an LLM on required versus preferred years. The one study I found is a fine-tuned classifier with weak labels, and it does not show LLMs beat regex. [S]

LLM second pass design:
- Schema: `{ required_min: int|null, required_max: int|null, preferred_min: int|null, evidence_quote: string|null, alternative_to_degree: boolean }`.
- Reject any answer whose `evidence_quote` is not a substring of the JD after whitespace normalization. This makes hallucinated numbers detectable without trusting the model. [U synthesis]
- Run only on rows with `minYears == null` and a freshness or strict-tier candidate. This keeps the call count small.
- Measure before enabling. Build a labeled set of 150 to 300 JDs from the saved inventory. Report accuracy separately for required, preferred, and null. The null rows are where the errors show up. [U]

## C. Freshness

### Schema.org and Google fields

- `datePosted` is the publication date of the listing, in ISO 8601. Google says it is the original date the employer posted the job and should stay fixed. [V] https://schema.org/JobPosting ; [V] https://developers.google.com/search/docs/appearance/structured-data/job-posting
- `validThrough` is the date after which the posting is not valid. Google requires it for postings that have an expiration date, and says to leave it out if the job never expires or the date is unknown. [V] https://developers.google.com/search/docs/appearance/structured-data/job-posting
- Google says "We don't allow expired job postings." Remove them, or keep them with a past `validThrough`, or return 404 or 410. [V] https://developers.google.com/search/docs/appearance/structured-data/job-posting
- Google's content policy, as reported in 2021, says not to mask old jobs as new and not to update `datePosted` when the job has not changed. [S] https://www.searchenginejournal.com/google-launches-new-structured-data-for-job-listings/413345/ . The current policy page was not opened. [U for current wording]

### Portal and ATS date manipulation

- Many ATS systems repost listings. One ATS guide says a refreshed job gets a new posted date and a new board ID in feeds. [S] https://ats-guide.zendesk.com/hc/en-us/articles/4409715272215-Job-Posting-AutoRefresh
- A GitHub issue reports `posted_at` on SuccessFactors and Workday as a repost or refresh date that moves forward, which makes "posted within N days" show old jobs as new. [S] https://github.com/sarthakjain004/headstart/issues/696
- JobSpy's README says `hours_old` uses when a job was added to Indeed, while `date_posted` reflects when the employer published it. The two can differ by weeks. [V] https://github.com/speedyapply/JobSpy (README summary via fetch)

Repo state: `classifyFreshness` in `job-pull/freshness.mjs` already drops Workday LIST `postedOn` and unverified Personio dates. It does not use the portal's added date as `postedAt`. [L by reading] This matches the rules above.

### Trustworthy first-seen date

First-seen is useful, but in one direction only. If the posting date is P and first-seen is F, then P is at or before F. So age at today is at least today minus F. [U, logic]

This means:
- First-seen proves a job is at least N days old. If F is 15 days ago and `postedAt` is null, the job cannot be inside the 14-day window. It can be rejected safely. [U]
- First-seen cannot prove a job is fresh. A new listing that was published a month ago and first crawled today looks new. [U]
- Keep `firstSeenAt` in crawler SQLite. Do not write it into `postedAt`. [U]

### Detecting expired or closed listings

Use signals in this order. Stop at the first one that gives a clear answer.

1. Direct HTTP. A 404 or 410 means gone. Confirm before acting. [V for the codes] https://developers.google.com/search/docs/appearance/structured-data/job-posting
2. JSON-LD `validThrough` in the past means expired. Already implemented in `extractDetails` in `crawler/original-listing-resolver.mjs`. [L by reading]
3. Provider status words. The repo already maps `closed`, `expired`, `filled`, `withdrawn`, and `removed`. [L by reading]
4. ATS API absence. A job missing from a public API list is weak evidence. Require absence on several consecutive runs and a failed direct check before marking it expired. [U]
5. Soft 404 pages that return 200 with a "not found" body. Vendor guidance says to check for redirects to the careers home page and for missing job anchors. [S] https://www.scrapeless.com/en/wiki/what-is-a-soft-404 (vendor blog, low weight)

Rule for the pipeline: blocked, login, and shell pages must never count as absence. The repo's `looksBlocked` and `looksMalformed` already route them to verification. [L by reading]

## D. Employment type and remote eligibility

### Structured signals

- Employment type: schema.org `employmentType` is free text with examples "full-time, part-time, contract, temporary, seasonal, internship". There is no closed enumeration. [V] https://schema.org/JobPosting
- Ashby public API uses a closed set: `FullTime`, `PartTime`, `Intern`, `Contract`, `Temporary`. [V] https://developers.ashbyhq.com/docs/public-job-posting-api
- Lever's employment field lives under `categories.commitment`, not at the top level. [V] https://github.com/lever/postings-api
- Remote: schema.org `jobLocationType` uses TELECOMMUTE for jobs that may or must be remote. Google requires TELECOMMUTE for 100% remote jobs and says those jobs must be fully remote. [V] https://developers.google.com/search/docs/appearance/structured-data/job-posting
- Google's `applicantLocationRequirements` lists where applicants may live. It is required for 100% remote jobs with a location limit, and it must not be used for visa or citizenship rules. [V] https://developers.google.com/search/docs/appearance/structured-data/job-posting ; [V] https://schema.org/JobPosting
- Lever's `workplaceType` is one of unspecified, on-site, remote, or hybrid. [V] https://github.com/lever/postings-api

Priority: structured fields first (Ashby `isRemote`/`workplaceType`, Lever `workplaceType`, JSON-LD `jobLocationType` and `applicantLocationRequirements`), then the text rules in `job-pull/eligibility.mjs`.

## E. Bot challenges, shell pages, and login walls

Principle for this repo: detect and report. Do not describe or add ways to get past a challenge. The goal is that a blocked page is reported as failed, not as an empty result.

### Cloudflare

- A challenge response carries `cf-mitigated: challenge`. This is the primary signal. The header value is `challenge` and no other value is valid. The content type is `text/html`. [V] https://developers.cloudflare.com/cloudflare-challenges/challenge-types/challenge-pages/detect-response/
- The official page does not document status codes or body markers for detection. Do not build detection on them alone. [V] same URL
- Third-party guides suggest body markers such as "Just a moment" and `challenges.cloudflare.com`. These are fallbacks, not official signals. [S] https://dev.to/bshahin/managed-vs-interactive-cloudflare-challenge-how-to-tell-and-why-it-changes-your-fix-3in0
- A header-only check misses some JavaScript detections that return 200 with no challenge header. [S] same DEV article and https://http.dev/cf-mitigated (describes the header as unofficial; Cloudflare's own docs are the better reference). [U for the 200-case detail]

### What the repo does

`looksBlocked` in `crawler/original-listing-resolver.mjs` checks:
- statuses 401, 403, 407, 429, 451, and
- a body regex `CAPTCHA_HINT` (includes "captcha", "access denied", "attention required", "verify you are human"), only when the body is under 50,000 characters.

Gaps found by reading [L by reading]:
- It does not read the `cf-mitigated` header. `headersOf` already exists and is used only for redirects. A Cloudflare challenge returning 200 or 503 with that header would not be caught unless the body also matches.
- "Just a moment" is not in `CAPTCHA_HINT`.
- "access denied" and "attention required" can appear in ordinary job text. The 50 KB limit helps but does not remove the risk. A false block is safe (the lead goes to verification), but it hides real jobs.

### Shell pages and login walls

Vendor guidance, low weight [S]:
- Separate outcomes: blocked, login wall, JS shell needing a render, valid empty result, and extraction failure. Only the first two and the last one should block a run. https://webscraper.io/blog/empty-pages-consent-screens-and-bot-challenges-telling-them-apart (title seen; body not opened)
- Signals for a shell: empty root node, no JSON-LD, no job title element, hydration-only payload, very few visible tokens. [S] https://dev.to/hasdata_com/building-a-production-ready-job-board-scraper-with-python-pgd (snippet)

Suggested outcome set for `daily` reporting [U synthesis]:

| Outcome | Trigger | Pipeline effect |
|---|---|---|
| `EXPIRED` | 404 or 410, or past `validThrough`, confirmed on a later run | Remove after repeated evidence |
| `BLOCKED` | `cf-mitigated: challenge`, 401/403/407/429/451, or block marker | Source degraded. Never counted as absence. |
| `LOGIN_WALL` | sign-in form or redirect to login | Source degraded |
| `NEEDS_RENDER` | shell with no job content | Route to the API endpoint if one exists, else report |
| `EMPTY_VALID` | real page with zero results | Counts as zero, healthy |
| `EXTRACTION_FAILED` | content present, selectors miss it | Alert. Usually a site change. |

## F. Pipeline reliability for a solo daily job

### What open-source tools do

JobSpy (https://github.com/speedyapply/JobSpy) is the closest public reference. Facts from its README via fetch [V, summary by tool]:
- Supports LinkedIn, Indeed, Glassdoor, ZipRecruiter, Bayt, BDJobs, and Naukri. Google Jobs was listed as unavailable.
- LinkedIn is the most restrictive. The README says it usually rate-limits around page 10 per IP.
- Glassdoor rate-limits after about 30 requests per IP. The README links this to `fetch_description`.
- Each search is capped at about 1,000 jobs.
- A 429 means too many requests. The README suggests waiting and using a proxy.
- The README does not address terms of service. [V]

What JobSpy does well: one function returns a dataframe with a site column, and it keeps the per-site failure visible. What it does badly for this repo: the output has no per-source terminal status, no first-seen date, no identity key, and no eligibility gate. It is a scraper, not a pipeline. [U synthesis]

### Practices to adopt

- Per-stage funnel with one counter per stage, plus a terminal status per source: `ok`, `empty_valid`, `blocked`, `failed`, `omitted_by_budget`, `not_run`. The handoff says this exists. The check to run is that every intended source has exactly one terminal status in the daily report, with no silent gap. [U]
- Idempotent reruns. `stableCandidateId` in `job-pull/candidate.mjs` hashes `canonicalUrl`, `jobId`, and the dedup key. If two URL variants of one requisition exist, they get two IDs and the rerun inserts a duplicate. Hash only the dedup key, or check the ID against the ledger on the dedup key. [L by reading; U on the failure rate]
- Canary: the repo's own gate is seven consecutive valid canary runs with matching manual inventory. [V] `docs/SYSTEM-REFERENCE.md` in this repo. Keep it. Add a check that a known-good requisition (a fixed saved fixture) resolves to the same key on every run.
- Freeze a replay fixture from each source. The handoff's replay approach is the right idea. [V repo doc]
