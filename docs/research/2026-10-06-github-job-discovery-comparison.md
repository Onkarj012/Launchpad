# GitHub job discovery and matching projects

Research snapshot: 6 Oct 2026. I inspected source at the pinned revisions below and did not run any project, call a job board, use an account, or test live yield. GitHub commit dates and licenses are repository metadata; feature claims below are limited to code paths I read. README and workflow claims do not prove operational yield.

## What the current run says

In the run under comparison, 868 observations produced 817 geography rejects and 51 location passes. Title checks reduced those to 5, experience checks to 2, freshness to 1, and unknown employment evidence left 0 verified, scored, or selected roles. A zero-role result is a failed product outcome for the daily shortlist goal. These counts do not establish that the later gates are wrong. They do show that source and query composition deserve attention before relaxing eligibility.

Three projects merit the closest follow-up: [JobSpy](https://github.com/speedyapply/JobSpy) for a bounded India-first portal experiment, [JobNavigator](https://github.com/vesaias/JobNavigator) for a fuller discovery and resume-scoring workflow, and [role-radar](https://github.com/hemantk1539-creator/role-radar) for India-specific source composition and per-source health reporting. None can replace Launchpad's strict experience, freshness, location-authorization, employment, and first-party verification gates.

## What can transfer, and what Launchpad already has

Launchpad already has source budgeting and Pune/India board ranking in [the board registry](../../crawler/board-registry.mjs), plus source lanes in [Normal mode](../../job-pull/normal-sources.mjs), freshness, experience and employment gates, scoring, and measured funnel reporting in [the funnel report](../../job-pull/funnel-report.mjs). The status note says freshness, remote-eligibility, and location-preset gates are locally implemented, while production verification remains open. Rebuilding a universal ATS layer, adding generic location ranking, or replacing the scorer with embeddings would repeat capabilities or act after the main loss.

The distinct ideas worth adapting are narrower:

- Put explicit city/country and role/seniority terms into the source query itself, before fetching broad ATS inventories. The 817/868 geography rejection is the strongest measured reason to try this.
- Treat third-party India-board results as discovery leads and keep first-party detail, date, experience, employment, liveness, and original-route checks in Launchpad.
- Preserve unknown dates and unknown location as unknown. The daily bot lets both through its respective filters, while DailyJobMatch fabricates a current date for an absent one.
- Keep adapters' submitted filters and observed output separate. The JobSpy consumer's comments identify an Indeed job-type-filter issue, and its post-filter compensates locally.
- Reject unrecognized search/filter parameters with an explicit diagnostic. This is a useful fail-closed API pattern from freehire, though it is not a source-yield fix.

## Prioritized experiments

These are proposed bounded, read-only experiments. They do not crawl boards now, require accounts, or authorize credentials, sends, writes, or auto-apply. Apply the normal source safety and request budgets if later run.

1. **India/Pune query partition, 45 minutes offline plus one approved bounded source pass.** Build a read-only replay plan from the current source registry: Pune/PCMC corridor, India-remote with explicit authorization, then matching title families and graduate/associate terms. Compare its requested query set with generic ATS rows. During a future live run, record each stage as raw → Pune/India-qualified → early-career → detail verified → scored → selected. Success means geo rejection falls below the current 94.1% without admitting ineligible locations, while freshness and employment remain fail-closed. Stop if source requests exceed the existing budget.
2. **JobSpy Naukri adapter calibration, 30 minutes and at most 12 GETs in a later approved pass.** Target Pune keywords from AI/ML, Python backend, full-stack, and graduate software engineering. Compare adapter parameters with captured payload evidence, keep the adapter's experience text as unverified, and send candidates through existing first-party resolution. Record HTTP 406 separately as source unavailability, not zero jobs. Measure unique raw rows and every funnel stage against the same keywords/dates from a replay baseline. Success is at least one detail-verified, eligible, scored result in the sample without any weakening of gates. Do not infer 10 daily roles from this sample.
3. **Hosted Naukri actor decision gate, 20 minutes before any use.** First get an actor input/output contract and a hard spend cap from public documentation; no token or paid run in this research. Compare exact Pune, experience, job type, work mode, freshness, and detail fields with JobSpy. Success requires documented filter semantics, bounded cost, and a clear first-party verification path. If the actor source is unavailable or prices cannot be bounded, stop with no account setup.
4. **Query mix versus broad-board control, two runs on the same approved date window.** Keep current eligibility/scoring fixed. Compare current broad ATS composition with targeted portal/search lanes, reporting raw → geography → title → experience → freshness → verified employment → scored → selected, source by source. Success is a higher number of eligible, verified, scored roles per request and shorter time to one such role; the target remains 10–20 per day, but neither run alone proves recurring supply.

## Evidence limits

- I inspected 10 repositories and 34 implementation/config/workflow files at the pinned revisions. I read metadata through the public GitHub API and source through raw GitHub URLs. The connector had no active GitHub connection.
- I did not inspect or crawl actual job boards, run project code, verify any repository's current runtime, reproduce a daily schedule, or benchmark yield. No project claim proves 10–20 fresh, eligible roles per IST day for this profile.
- Some candidates rely on third-party services: JobSpy itself is a local Python library; the Naukri wrapper uses paid Apify; the daily bot can use paid Apify/JSearch and a model API; the India matcher uses Gemini plus JSearch/RapidAPI. Google Cloud Talent Solution appears in the US-oriented pipeline's custom source path.
- The public project sample includes a broad ATS aggregator and broad scraping/matching prototypes. It is not six independent India-verified data sources. Several are useful mainly as cautionary examples, and no code from projects without a license should be reused.
- Branch tip, license, and commit date are a point-in-time snapshot. The final source commit dates above were queried from GitHub metadata on 6 Oct 2026. README claims and repository activity do not establish data freshness or source reliability.
